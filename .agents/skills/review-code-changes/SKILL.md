# 代码变更审查

默认任务是找出并解释变更中的实际问题，而不是修改代码。用户明确要求“审查并修复”时，先完成审查，再修复确认的问题。

## 确定审查范围

先从用户请求中确认范围：

- 当前未提交变更；
- 某个提交或 `base...head` 范围；
- 某个 PR；
- 指定文件、模块或功能。

未指定时，以当前工作区相对 `HEAD` 的变更为主，同时检查已暂存和未暂存内容。不要擅自把当前分支相对默认分支的全部历史当作目标。

开始审查前：

1. 查看 `git status --short` 和变更概览。
2. 阅读适用的 `AGENTS.md` 或仓库规范。
3. 获取实际 diff，而不是只看文件名或提交说明。
4. 对未跟踪但属于本次任务的源码文件，读取其内容。
5. 如果没有任何变更，明确说明，并询问用户要审查的提交、分支或 PR。

如果用户指定了 PR，优先读取 PR 的实际 diff 和元数据；不要用本地工作区中的无关修改代替 PR 内容。

## 审查重点

优先寻找会改变真实行为的问题：

- **正确性**：边界值、空值、状态转换、分支遗漏、错误传播和资源释放。
- **集成契约**：调用方、返回值、序列化格式、外部 API 字段和协议假设是否一致。
- **回归风险**：删除或替换逻辑后，旧的调用方、测试和兼容路径是否仍可工作。
- **持久化和迁移**：数据库 schema、迁移、旧数据兼容、事务边界、查询排序与索引。
- **并发与生命周期**：协程取消、重复请求、竞态、后台恢复、播放器/监听器/流是否正确释放。
- **安全与隐私**：权限、敏感数据落盘或日志、注入、路径穿越、不安全的反序列化和信任边界。
- **性能**：仅报告能从代码证明的明显放大，例如重复扫描大对象、主线程 I/O、无界缓存或 N+1 查询。
- **可验证性**：高风险行为改动是否有对应测试，失败时错误是否可观察。

不要因为个人风格、格式偏好或“可以更抽象”提出 finding。纯重构建议只有在会造成实际维护或正确性风险时才报告。

## 证据标准

每个 finding 必须能说明：

1. 什么输入、操作或状态会触发；
2. 会发生什么错误、回归或风险；
3. 哪段变更导致了它；
4. 哪个调用方、契约、测试或数据约束支持该判断。

报告前主动验证：

- 查看被修改符号的定义、调用方和相邻测试；
- 对比变更前后的行为，而不只看新增代码；
- 检查异常、取消、重试和空数据路径；
- 读取 schema、接口定义或序列化模型确认字段兼容性；
- 对疑似问题运行最小相关测试、构建或静态检查，前提是当前环境允许。

不要把一个假设写成确定缺陷。无法完全验证但风险重要时，放到“待确认风险”，说明缺失的信息和验证方法。

## 严重级别

使用以下级别帮助用户排序，但不要机械地按代码行数判断：

- **P0**：广泛数据丢失、安全突破、不可恢复损坏或生产完全不可用。
- **P1**：高概率的用户可见错误、主要功能失效、严重回归或数据一致性问题。
- **P2**：特定但有现实触发条件的错误、兼容性或边界问题。
- **P3**：影响有限的小缺陷或明确可证明的维护风险。

没有实际影响的猜测不要为了凑级别而报告。

## 输出格式

先给 findings，按严重级别从高到低排列。每项使用简洁标题，并包含：

- 文件路径和准确行号；
- 触发条件；
- 实际影响；
- 支持判断的证据；
- 建议的修复方向。

示例结构：

```markdown
### [P1] 保存后仍使用旧状态

[WorkRepository.kt](/abs/path/WorkRepository.kt:42)

触发：更新完成后继续读取缓存中的旧对象。
影响：界面会显示已删除的作品，直到进程重启。
证据：这里绕过 DAO 的 Flow 更新，而 UI 只订阅缓存。
建议：在同一次状态更新中刷新缓存，或让 UI 继续观察数据库。
```

如果没有 finding，直接说明“未发现需要阻止合并的问题”，然后列出：

- 仍未验证的高风险路径；
- 实际运行过的测试、构建或 Lint；
- 因权限、环境或缺失依赖而无法执行的检查。

最后再列出需要用户确认的假设或问题。不要把总结放在 findings 前面。

在 Codex Desktop 支持行内审查评论时，为每个可操作的 finding 输出对应的 `::code-comment{...}` 指令，并保持行号来自当前 diff。普通 Markdown 中仍保留 findings 列表，便于没有行内 UI 时阅读。

## 边界

- 审查不自动授权修改代码、提交、推送、发评论或改变外部系统。
- 不要顺手修复无关问题，也不要因为发现小问题就扩大审查范围。
- 性能优化、重构和测试补齐只在它们解决已证实风险时纳入建议。
- 如果用户要求修复，修改后重新检查原 finding，并运行与风险相称的验证。
